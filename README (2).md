## Задание 1. План адресов

VPC: `10.18.0.0/16`

| Подсеть | Зона доступности | Диапазон | Первый и последний адрес для экземпляров | Доступно |
|---|---|---|---|---|
| public-a | eu-central-1a | 10.18.0.0/24 | 10.18.0.4 - 10.18.0.254 | 251 |
| public-b | eu-central-1b | 10.18.1.0/24 | 10.18.1.4 - 10.18.1.254 | 251 |
| private-a | eu-central-1a | 10.18.10.0/24 | 10.18.10.4 - 10.18.10.254 | 251 |
| private-b | eu-central-1b | 10.18.11.0/24 | 10.18.11.4 - 10.18.11.254 | 251 |

**Почему доступных адресов не 256? Какие адреса занимает AWS?**
AWS резервирует 5 адресов в каждой подсети: `.0` адрес сети, `.1` маршрутизатор VPC, `.2` DNS-сервер VPC, `.3` резерв AWS на будущее, `.255` broadcast (в VPC не поддерживается, но адрес занят). Остаётся 256 - 5 = 251.

**Сколько ещё подсетей /24 поместится в VPC?**
В /16 помещается 256 подсетей /24. Четыре уже заняты, свободно ещё 252.

## Задание 2. VPC и подсети

Создана VPC `timecapsule-dev-vpc` (10.18.0.0/16), включены DNS resolution и DNS hostnames. Созданы четыре подсети по таблице из задания 1, все с обязательными тегами.

**Является ли public-a сейчас публичной? Почему?**

## Задание 3. Internet Gateway и таблицы маршрутов

- Создан и подключён к VPC `timecapsule-dev-igw` (состояние Attached).
- `timecapsule-dev-public-rt`: маршрут `0.0.0.0/0` → Internet Gateway, связана с public-a и public-b.
- `timecapsule-dev-private-rt`: без дополнительных маршрутов, связана с private-a и private-b.
- В public-a и public-b включено автоназначение публичных IPv4-адресов.

**Какой маршрут есть в обеих таблицах? Что он даёт? Куда уйдёт пакет из private-a на 8.8.8.8?**
В обеих таблицах есть `10.18.0.0/16 → local`. Он создаётся автоматически и обеспечивает связь между всеми ресурсами внутри VPC, в том числе между зонами доступности. Пакет из private-a на 8.8.8.8 никуда не уйдёт: подходящего маршрута нет (в private-rt только local), поэтому он будет отброшен.

## Задание 4. Security Group

| Группа | Входящее правило | Источник |
|---|---|---|
| bastion-sg | SSH (22) | My IP |
| web-sg | HTTP (80) | 0.0.0.0/0 |
| web-sg | SSH (22) | bastion-sg |
| db-sg | PostgreSQL (5432) | web-sg |
| db-sg | SSH (22) | bastion-sg |

**Почему в db-sg источником указана группа web-sg, а не адрес веб-сервера или диапазон 10.18.0.0/16?**
Адрес сервера может измениться при его пересоздании, и правило перестанет работать. Диапазон 10.18.0.0/16 пустил бы к базе все серверы VPC, включая bastion. Группа в качестве источника пускает ровно те экземпляры, которые в неё входят, независимо от их адресов.

## Задание 5. Экземпляры

| Роль | Имя | Подсеть | Публичный IP | Security Group |
|---|---|---|---|---|
| bastion | timecapsule-dev-bastion | public-b | да | bastion-sg |
| web-server | timecapsule-dev-web | public-a | да | web-sg |
| db-server | timecapsule-dev-db | private-a | нет | db-sg |

На web-server через User data установлен nginx, страница показывает имя сервера и приватный адрес `10.18.0.120` из подсети 10.18.0.0/24. SSH на web и db настроен через bastion (`ProxyCommand` в `~/.ssh/config`), подключение `ssh bastion`, `ssh web`, `ssh db` работает.

**Почему db-server не может скачать пакеты, хотя web-server это делает? Что нужно добавить в сеть?**
У web-server есть публичный адрес и маршрут в Internet Gateway. У db-server нет ни публичного адреса, ни маршрута `0.0.0.0/0` в private-rt, поэтому запрос не доходит до интернета и завершается таймаутом. Нужен NAT Gateway в публичной подсети и маршрут на него из private-rt: он пропускает только исходящие соединения, и db-server остаётся недоступным из интернета.

## Задание 6. Временный NAT Gateway

Создан `timecapsule-dev-nat-a` в public-a с Elastic IP `timecapsule-dev-nat-a-eip`, в private-rt добавлен маршрут `0.0.0.0/0` → NAT. На db-server установлен PostgreSQL 16, настроены `listen_addresses = '*'` и `pg_hba.conf` (доступ из 10.18.0.0/24 по scram-sha-256), создан пользователь `student` и база `lab3`. После установки NAT Gateway удалён, маршрут (Blackhole) убран, Elastic IP освобождён.

**Какой адрес вернула команда `curl https://checkip.amazonaws.com`? Почему это не адрес db-server?**
Адрес `52.57.91.169`, это Elastic IP NAT Gateway. NAT подменяет приватный адрес отправителя на свой публичный, поэтому все серверы приватной подсети выходят в интернет с общего адреса шлюза. Собственного публичного адреса у db-server нет.

**Три механизма ограничения доступа к базе. Что произойдёт, если ошибиться только в одном?**
1. Сеть (нет публичного адреса и маршрута из/в Internet Gateway): до сервера нельзя добраться из интернета.
2. Security Group db-sg: пропускает на порт 5432 только web-sg.
3. `pg_hba.conf`: PostgreSQL разрешает вход только указанным пользователям, базам и адресам, и требует пароль.

Если ошибиться в одном, остальные продолжают защищать базу (многоуровневая защита), но при ошибке сразу в нескольких слоях база окажется открытой.

**Почему PostgreSQL продолжает работать после удаления NAT Gateway? Что делать для обновлений безопасности?**
NAT нужен только для исходящих соединений (скачивание пакетов). Сам сервис базы работает локально и принимает подключения из VPC. Для установки обновлений безопасности нужно снова временно создать NAT Gateway, добавить маршрут, выполнить `dnf update`, затем всё удалить.

## Задание 7. Проверки

**Доступ к базе.** С web-server установлен клиент `postgresql16`, команда `psql -h 10.18.10.171 -U student -d lab3 -c "SELECT version();"` вывела версию PostgreSQL 16.15.

**Security Group в действии.** Проверка порта 5432: с web-server результат `open`, с bastion результат `closed`.

**Почему с web-server порт открыт, а с bastion нет, хотя оба в одной VPC и маршрут есть?**
Маршрут только доставляет пакеты, а решение о пропуске принимает Security Group. В db-sg порт 5432 разрешён только для web-sg. Bastion в эту группу не входит, поэтому соединение отбрасывается.

**Изоляция базы.** `curl -m 5 https://github.com` с db-server завершился таймаутом.

**Почему запрос не проходит? Можно ли из интернета подключиться к порту 5432 db-server?**
Запрос не проходит, потому что в private-rt нет маршрута в интернет (маршрут, адрес, фильтры): исходящему пакету некуда идти. Из интернета подключиться нельзя: у сервера нет публичного адреса, из Internet Gateway нет маршрута в private-подсеть, а db-sg пускает только web-sg.

**Network ACL.** В Network ACL VPC добавлено правило 90 (All traffic, мой внешний IP/32, Deny). После этого `ssh bastion` завис, а сайт выдал `ERR_CONNECTION_TIMED_OUT`. С телефона через мобильный интернет сайт открылся. После удаления правила SSH и сайт работают.

**Почему заблокировано и SSH, и сайт, хотя Security Group не менялись? Почему с телефона открывается? Почему номер меньше 100?**
Network ACL работает на границе подсети и проверяется раньше Security Group, а правило 90 запрещает весь трафик с моего адреса. С телефона сайт открывается, потому что у него другой внешний IP, и правило его не затрагивает. Правила ACL проверяются по возрастанию номеров до первого совпадения. Правило 100 разрешает весь трафик, и если бы Deny имел номер больше 100, до него дело бы не дошло.

**Как по тегам найти все ресурсы для удаления после проекта? Зачем тег Owner, если аккаунт личный?**
В Tag Editor нужно искать по `Project = timecapsule` (при необходимости и `Lab = lab3`): список покажет всё, что относится к проекту. Тег Owner показывает, кто отвечает за ресурс и кого спросить о нём. В рабочем аккаунте это обязательно, поэтому соглашение отрабатывается и в личном.
